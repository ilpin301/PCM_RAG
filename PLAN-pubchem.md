# Plan: Shape 1 — PubChem enrichment of PCM_RAG chemical entities
_Locked via grill — by Claude + ilpin301 · revised after GLM Round 1 · revised 2026-09-29 after GLM Round 4 (post-implementation re-review)_

## Goal
Enrich the existing LightRAG knowledge graph (PCM_RAG, localhost:9622) with structured chemical data from PubChem. For each chemical entity already present in the graph, fetch canonical formula, molecular weight, SMILES, IUPAC name, and — where PubChem carries it — melting point, then attach those facts directly onto the existing entity node's `description` so they become part of the bge-m3–embedded, query-retrievable graph. Note: PubChem does NOT reliably carry enthalpy of fusion (ΔHfus); that is out of scope here and belongs to a future DIPPR/literature source. Compound-only; OpenAlex deferred. No new documents ingested, no MinerU, server stays up throughout.

## Approach
1. **Enumerate candidate chemical entities from the persisted graph file (NOT `/graphs`).** Read `data/rag_storage/graph_chunk_entity_relation.graphml` directly (actual tree is `lightrag/data/rag_storage/...`; since `enrich_pubchem.py` lives at `lightrag/enrich_pubchem.py`, resolve this path from the script's own dir via `Path(__file__).parent / "data/rag_storage/..."`, NOT cwd). Note: this candidate list is a point-in-time snapshot — each `aedit_entity` in step 5 flushes the graphml mid-run, but that's harmless since step 1 reads names only, once. Reason (GLM Round 1 [HIGH], verified): `GET /graphs?label=*` is capped at `min(max_nodes, MAX_GRAPH_NODES=1000)` (networkx_impl.py:511, config default 1000) and the graph has 1786 nodes — the API would silently drop ~786 low-degree nodes (exactly the obscure compounds we target) and never surface `is_truncated`. Reading the graphml file is complete and uncapped. Build the candidate set as a **UNION of two paths (Option C), deduped by entity name** — names+types only, read directly from the graphml (uncapped), NOT the base description (that is re-read fresh at write time, step 5):
   - **(a) TYPE path:** all nodes whose `entity_type` ∈ {`naturalobject`, `material`, `substance`} (grounded: no `chemical` type exists; these three hold the obvious chemicals — `naturalobject`=91, `material`=4, `substance`=1, ~96 nodes). This path catches bare metals/elements like "Gallium", "Indium" whose names carry no chemical token, which the regex path (b) would miss.
   - **(b) REGEX path:** nodes of type `concept` (372) or `artifact` (335) whose **name matches a chemical-name regex** — tokens `acid|hydrate|paraffin|wax|glycol|erythritol|eutectic|oxide|nitrate|sulfate|sulphate|chloride|carbonate|hydroxide|stearic|palmitic|lauric|myristic|capric|oleic|PEG|Ag2O|Al2O3|CuO|ZnO|graphene oxide`, PLUS a simple formula pattern `^[A-Z][a-z]?\d` or the name contains `·`/`H2O`/`Na2`/`CaCl2`. Real discrete compounds are misfiled here (e.g. "Lauric Acid PCMs", "Paraffin", "Ag2O Nanoparticles", "C10"/decane, "Al2O3-CuO Hybrid"). This regex is a **cheap candidate-widener only** — false hits cost nothing because the LLM-judge (step 2) is the real gate.
   Union (a)+(b), dedupe by entity name. **Observed candidate set: 455 candidates on the 1786-node graph** (MODE=full run 2026-08-12); the graph has since grown (78 docs), so the earlier ~120 estimate is void and a **MODE=dry run on the current base is MANDATORY before any MODE=full**, to re-measure candidate count and judge/PubChem cost. Output = candidate list of entity names + types only. **The graphml attribute key for `entity_type` must be resolved at runtime** from the graphml `<key for="node" attr.name="entity_type">` registry, never hardcoded (the script currently hardcodes `K_TYPE = "d1"` — correct today, but networkx assigns `dN` ids by first-encounter order, so a rewrite could shift it silently).
2. **LLM-judge gate (glm-5.3 via z.ai, `asyncio.Semaphore(2)`).** For each candidate name, one classification call: "Is this a discrete chemical compound whose properties are relevant to phase-change-material research? If yes, return the canonical compound name (and formula if known) suitable for a PubChem name lookup; if no, return SKIP." Concurrency capped at 2 (z.ai code 1305 is a concurrency limit, per memory `project_zai_429_behavior` — never batch-flood). Implementation is `Semaphore(2)` + retry backoff (no serial fallback). The judge now also receives `concept`/`artifact` candidates (via the step-1 regex path) and must **reject non-compound abstractions** ("CO2 Emissions", "Eutectic Structures", "Sp2 Bonds") and multi-component composites with no single CID ("Al2O3-CuO Hybrid Nano-PCM"), while **extracting the base compound** only from pure-material FORM suffixes that don't change thermophysics — `Nanoparticles|Powder|Nanofluid|Nanowire` — e.g. "Ag2O Nanoparticles" → "silver(I) oxide". **SYSTEM/COMPOSITE SKIP rule (provenance-leakage guard):** the judge MUST return SKIP for any candidate whose name denotes a system / composite / derivative — trigger tokens `PCM|PCMs|Eutectic|Hybrid|infused|Nano-PCM|Ne-PCM|Doped|Composite|Mixture|Blend|Bi-`, or any multi-element hyphenated token of the form X-Y or X-Y-Z (e.g. "Al2O3-CuO") — **EVEN WHEN a single base compound and CID are extractable** (e.g. "Lauric Acid PCMs" → SKIP, "Al2O3 Nanoparticle-infused Ne-PCM" → SKIP). Rationale: writing a correct CID's pure-compound thermophysics (e.g. Al2O3 mp 2072°C, lauric acid mp 44°C) onto a node that is actually a composite/system/eutectic = silent WRONG melting point that RAG could retrieve and cite — the exact poisoning this gate prevents. Drops cement phases (Portlandite, Ettringite, C-S-H Gel), gases (N2), non-compounds (PCM Acrylate Ion); normalizes messy names ("Paraffin-based 116 Wax" → "paraffin wax"/"hexadecane"). Cache verdicts to `data/enrich_cache/judge.json` — only successful verdicts are cached. **Reply parsing:** the judge reply is matched case-insensitively for the first `COMPOUND:` or `SKIP` token anywhere in the reply (not only line 1 — fenced or preamble replies otherwise mis-parse as SKIP). **Judge failures:** calls that fail after retries are counted as a separate `judge_error` stat, never folded into skipped_judge and never cached; the run aborts before any writes if judge_error exceeds 10% of candidates. **`--refresh`** also re-judges cached SKIP verdicts (bypassing only the marker check would freeze a mis-parsed SKIP in judge.json forever).
3. **PubChem fetch (per judged compound), with explicit rate/error handling.** Using the canonical name:
   - name→CID: `GET /rest/pug/compound/name/{name}/cids/JSON`. On **HTTP 404 → log "unresolved", continue** (never crash the run). Retries exhausted on 429/503/network errors → separate **"fetch_failed"** outcome (not "unresolved"), not cached, eligible again on the next run.
   - properties: `GET /rest/pug/compound/cid/{cid}/property/MolecularFormula,MolecularWeight,IUPACName,CanonicalSMILES/JSON`
   - synonyms (for the confidence check): `GET /rest/pug/compound/cid/{cid}/synonyms/JSON`
   - melting point (best-effort): `GET /rest/pug_view/data/compound/{cid}/JSON?heading=Melting+Point`
   - **Resolution confidence rule (concrete):** accept the CID only if the normalized-lowercase query name is an exact match of the resolved IUPAC name OR exactly equals (whole-string) any entry in the CID's synonym list. Else drop the node and log "unresolved". (PubChem `/name/` search is fuzzy and returns a list; do not blindly take `cids[0]`.)
   - **Melting-point pick rule (concrete):** from the pug_view Melting Point section, take the first numeric value whose unit is °C; if only °F/K, convert and annotate the value in the block as "(converted from °F)" / "(converted from K)"; guard that the pug_view `Number` field is a list before indexing; if the entry is a range, take the low end; if it says "decomposes"/no numeric °C value, write "not available". Never guess.
   - **Rate/HTTP budget:** obey BOTH PubChem limits simultaneously — ≤5 req/s AND ≤400 req/5-min/IP. ~5 calls/compound × ~96 candidates ≈ 480 calls → would exceed the 5-min cap at naive speed, so use a flat `sleep(0.8)` between calls (1.25 req/s = 375 calls/5 min, under both the 5/s and 400-per-5-min caps; 0.75 s would sit exactly at the 400 cap), OR a sliding-window counter capped at 390 calls per 5 minutes. Honor `Retry-After` on 503/429, back off on 503, and send a descriptive `User-Agent` + `From: ilpin301@gmail.com` header. Cache raw JSON to `data/enrich_cache/{cid}.json` (resolve from the script's own dir via `Path(__file__).parent / "data/enrich_cache/..."`, NOT cwd; re-runs then cost ~0 calls).
4. **Format facts as a delimited text block** (deterministic template, no LLM):
   ```
   <!--PUBCHEM_START-->
   PubChem facts (CID {cid}): Formula {formula}. MW {mw} g/mol. IUPAC {iupac}. SMILES {smiles}. Melting point {mp_or_not_available}. Source: PubChem CID {cid}.
   <!--PUBCHEM_END-->
   ```
5. **Idempotent read-modify-write via `/graph/entity/edit`, with a FRESH per-node read.** Immediately before writing each node (not from step 1): re-read the node's current description via `GET /graphs?label=<exact_name>&max_depth=1` (single-node query, well under the cap). If this fresh read returns an empty KnowledgeGraph (node renamed/deleted by hand between enumeration and write), log "gone" and skip that node. Reason (GLM Round 1 [MED]): `aedit_entity` REPLACES `description` wholesale; a stale base captured minutes earlier would clobber any WebUI/manual edit made in between. Then strip any existing PubChem block with a DOTALL regex — `re.sub(r'<!--PUBCHEM_START-->.*?<!--PUBCHEM_END-->', '', desc, flags=re.DOTALL)` (pug_view strings can contain newlines; non-DOTALL strip would let blocks stack and break the skip-check). Append the freshly-built block, then `POST /graph/entity/edit` with `{"entity_name": <name>, "updated_data": {"description": <new_desc>}, "allow_rename": false, "allow_merge": false}`. Attaches to the exact node (no re-extraction, no orphans); Persistence is per edit: `aedit_entity` → `_edit_entity_impl` → `_persist_graph_updates` (lightrag/lightrag/utils_graph.py:517) → `index_done_callback` on entities_vdb, relationships_vdb, graph and chunk-tracking storages. Vector storage is Qdrant since 2026-09-09 (upsert only buffers; embedding + Qdrant write happen in that flush), so each successful edit is embedded, written to Qdrant and the graphml before the call returns — no separate flush or ingest is needed, and `rag_sync.ps1 push` after the run captures it. Marker → re-runs replace (never stack) and doubles as the "already enriched" skip check.
6. **Wrap as `lightrag/enrich_pubchem.py`,** resumable (skip nodes whose fresh description already contains an up-to-date marker unless `--refresh`), logging each node's outcome: enriched / skipped-judge / unresolved / error. Server must be UP and idle — `aedit_entity` calls `check_pipeline_busy_or_raise`, so no ingest may run concurrently.
7. **Verify.** Query the RAG: "what is the melting point of paraffin wax?" → answer should cite the PubChem-injected value, not just paper text. Spot-check 2–3 enriched nodes via `GET /graphs?label=<name>` to confirm the PUBCHEM block is present and the original description survived above it. Cross-check the enriched-node count against the judged-yes count and the graphml candidate count (no silent drops).

## Key decisions & tradeoffs
- **Enumerate from the graphml file, not `/graphs`.** Avoids the 1000-node API cap that would silently skip low-degree compounds. File read is complete and offline; only a name/type list is taken from it, so staleness is irrelevant (the authoritative base description is re-read per-node at write time).
- **Source = existing graph entities (not raw text).** Facts attach to the exact node papers reference; no orphan "paraffin wax" vs "Paraffin-based 116 Wax" duplicates. Cost: can only enrich compounds already in the graph (acceptable — that's the goal).
- **LLM-judge gate + concrete confidence rule, not blind PubChem loop.** ~1/3 of candidates are cement chemistry / gases / non-compounds. Blind fuzzy name→CID would waste calls and silently write WRONG-compound properties. Judge + normalized-name/synonym match prevents graph poisoning.
- **Candidate enumeration = Option C (type ∪ regex-over-concept/artifact).** The TYPE filter catches bare metals/elements (Gallium, Indium) whose names carry no chemical token. The chemical-name regex over `concept`/`artifact` catches real compounds misfiled under those types — mostly nano-additives (Al2O3, CuO, Ag2O, ZnO, graphene oxide), relevant because this corpus is heavy on nano-enhanced PCM. Regex-only would miss the bare metals; type-only would miss the misfiled compounds — hence both, unioned. The union yielded 455 candidates on the 1786-node graph (2026-08-12), still well under blind whole-type widening of `concept`+`artifact` (≈707: concept 372 + artifact 335); cost must be re-measured with MODE=dry on the current base before MODE=full. The regex is best-effort (a candidate-widener), not exhaustive — the LLM-judge is the real gate.
- **Injection via `/graph/entity/edit`, not `/documents/text`.** Direct node update: no glm-5.3 re-extraction, no z.ai 1305 exposure on the write path, no merge ambiguity, server stays up. Trade: can't add brand-new compounds (out of scope).
- **Delimited RMW with fresh per-node read + DOTALL strip.** Idempotent, preserves original paper text, avoids clobbering concurrent edits, self-documents provenance, stays in the embedded description so it's searchable.
- **PubChem-only now; OpenAlex + enthalpy deferred.** Different targets/matchers/fields; PubChem doesn't carry ΔHfus reliably anyway.

## Risks / open questions
- **Judge cost/accuracy under z.ai limits.** 455 candidates observed (1786-node graph, 2026-08-12; more now) means ~455+ classification calls at Semaphore(2) with retry backoff; only successful verdicts are cached; judge_error abort threshold 10%. Re-measure with MODE=dry before MODE=full.
- **Disk graphml can lag server memory.** If WebUI edits were made since the last flush, nodes created that way are missed until a later run (snapshot semantics; documented, not fixed).
- **Regex pre-filter is not exhaustive.** It can still miss a compound that is BOTH misfiled under `concept`/`artifact` AND has no chemical token in its name. This residual gap is acceptable — the regex/judge combo is best-effort, not exhaustive.
- **Near-duplicate candidates across paths.** Many `concept`/`artifact` "compounds" duplicate a type-path node (e.g. "Paraffin" vs "Paraffin Wax"). Dedupe-by-name reduces but won't perfectly merge near-duplicates; the judge's canonical-name normalization plus the exact-node `/graph/entity/edit` write means each duplicate simply enriches its own node independently (harmless — no merge, no clobber).
- **PubChem coverage of PCM materials is uneven.** Eutectics, salt hydrates ("Na2SO4·10H2O"), trade-name waxes ("RT-116") often have no clean CID or no °C melting-point annotation. Expect a meaningful unresolved rate; log it, never force a match. Composites with no single CID are SKIPped by the judge; additionally, single-base systems (e.g. "Lauric Acid PCMs", "Al2O3 Nanoparticle-infused Ne-PCM") — where a base compound and CID ARE extractable — are now ALSO SKIPped by the step-2 SYSTEM/COMPOSITE rule, so pure-compound thermophysics never lands on a composite/system/eutectic node.
- **Melting point provenance is coarse.** pug_view aggregates values from many sources; the first-°C-value rule is a heuristic, not a curated selection. Acceptable for RAG context; the CID is always cited so a reader can verify.
- **`/graph/entity/edit` requires an idle pipeline.** Editing while serving queries is fine; editing during any ingest is blocked by `check_pipeline_busy_or_raise` — ensure no ingest runs.
- **Embedding drift.** Appending facts changes each entity's embedding and its retrieval behavior slightly. Expected/desired; before/after spot-check on 2 nodes in step 7.

## Out of scope
- OpenAlex / arXiv enrichment (separate future build).
- Enthalpy of fusion (ΔHfus) — PubChem is not a reliable source.
- Adding compounds NOT already in the graph (no `/documents/text` path here).
- Shape 2 (live tool at query time).
- Any change to the MinerU/rag_ingest.py pipeline or the embedding model.
- Enriching non-compound entity types (person, organization, method, etc.). Note: `concept`/`artifact` nodes are IN scope ONLY when their name matches the step-1 chemical-name regex (candidate-widener) — never wholesale; the vast majority of `concept`/`artifact` nodes remain excluded.
